### 고친 문제: mediapipe 1.x 가 Raspberry Pi 4 에서 바로 죽음

- 원인: 파이는 **Raspberry Pi 4 Model B** (Cortex-A72, `/proc/cpuinfo` Features 에 `aes` 없음). mediapipe 1.x 의 aarch64 휠은 AES 명령을 요구함. `import` 만으로는 안 죽어서 기존 설치 확인이 통과했음.
- 수정: `aivt deps` 가 파이 CPU 에 `aes` 가 없으면 `mediapipe==0.10.18` 설치 (Pi 4 에서 되는 최신). 설치 확인도 import 대신 **실제로 `hand_landmarker.task` 를 로드**해서 검사. (0.10.18 은 numpy 1.26.4 / opencv 4.11 같이 설치됨)
- Pi 5 등 AES 있는 CPU 는 기존대로 최신 mediapipe.

### [문제 1] 모터 속도 (CFG)
- 사실 확인: 원래부터 `motor_esp32.connect()` 가 연결(재연결 포함)할 때마다 `state.py` 값으로
  `CFG:MSL:3000`, `CFG:ACC:150`(=15.0Hz/ms), `CFG:M1I:0`, `CFG:M2I:1` 을 보내고 있었음.
  → 실제 가속도는 펌웨어 기본 3.0 이 아니라 **이미 15.0**. 요청한 `CFG:ACC:50`(5.0) 은 지금보다 **느려짐**.
- 변경: `--msl`(기본 **3500**), `--acc`(기본 **150**, 지금과 같음). `Motor` 가 `motor_esp32.start()` 전에
  `state.esp32_max_speed_hz / esp32_accel_rate` 를 바꿔 두므로 기존 connect() 가 매 연결마다 그 값을 보냄 (motor_esp32.py 수정 없음).
  시작 때 ESP32 의 `OK CFG:...` 응답으로 확인 → 안 오면 1번 더 보냄 → 결과 출력 (`[motor] 속도 설정 확인: ...`).
- 실행 중 `OK BOOT`(ESP32 재시작: 전원 흔들림/USB 재연결) 감지 → CFG 다시 보냄 + **추적 중지 경고**
  (재시작하면 펌웨어 위치가 0 으로 바뀌어 안전 리밋 기준이 틀어지므로).
- 참고: 펌웨어 속도 = min(MSL, 남은스텝×8). 작은 이동에선 MSL 이 거의 영향 없음
  (MSL 3500 에 닿으려면 남은 거리 ≥ 437스텝 ≈ 9.8 펌웨어° ≈ M1 물리 78°). 체감 속도는 게인/명령 이동량이 더 크게 좌우.

### [문제 2] 손을 놓칠 때 마지막 방향으로 "휙" 밀림 — 원인 (코드 확인)
- 사용자 추정("같은 오차를 현재 위치 기준으로 반복 적용")은 **아니었음**: `on_detection` 은 이미 촬영 순간 위치(PoseHistory) + 오차로 계산했음.
- 진짜 원인: `Tracker.command()` 가 제어 스레드에서 **50Hz 로 매번** `필터위치 + 속도 × (경과시간 + lead)` 를 다시 계산.
  검출이 없어도 목표가 마지막 속도 방향으로 계속 밀려 나감 — 놓친 뒤 `coast 0.25 + lead 0.12 = 0.37초` 분량,
  속도 상한 `vmax=150°/s`(사실상 무제한). 그래서 LOST 중 cmd 34/s, TRACK 중 cmd(46~53) > det(15).
  모터는 마지막으로 받은 (밀려 나간) 목표까지 계속 감 → "휙". 튐 검사(`jump_deg=40°`)도 너무 커서 무의미했음.
- 수정 (요청 1~5 그대로):
  1. 새 검출이 들어왔을 때만 목표를 1번 계산 → cmd/s ≤ det/s
  2. 목표 = 촬영 시각의 모터 위치(POS 를 **받은 시각**으로 기록, 30ms 간격 보간) + 오차×게인 + 예측(최대 `--max-lead-px 40`px 분량)
  3. 마지막 검출 후 `--lost-stop 0.2`초 지나면 `S` 1번 (손 사라짐 1초 → 제스처 STOP 때도 halt)
  4. 직전 추정보다 `--jump-px 150`px 넘게 튄 검출은 무시 (2번 연속까지, 3번째는 진짜 이동으로 보고 필터 리셋)
  5. 명령 1번 = 현재 위치에서 최대 `--max-step`(기본 화면 200px 분량 = M1 2.6° / M2 2.0° 펌웨어 단위, M1 물리 약 20°)
     → 부수 효과: 펌웨어 속도가 남은스텝×8 이라 최고 속도도 약 900Hz 로 묶임. 느리면 `--max-step 4` 등.
- 시뮬레이터 결과 (게인 일치, 손 6°/s 로 움직이다 놓침, `--lost-stop` 기본):
  | 시나리오 | 놓친 뒤 모터 이동 (예전 → 지금) | 손 마지막 위치 지나친 양 | 명령 수 |
  |:---|:---:|:---:|:---:|
  | 깨끗한 검출 | 1.99° → 0.33° | +2.14° → +0.58° | 84 → 27 |
  | 검출 60% 실패(블러) | 1.88° → 0.00° | +0.87° → −1.56°(못 미침) | 38 → 7 |
  | + 15% 엉뚱한 검출 | 0.82° → 0.01° | 추적 중 앞지름 1.49° → 0° | 33 → 8 |
  기존 sim: step 오버슈트 11.0→0.8px(1차) / 23.9→7.8px(2차), 정착 1.23→0.77s(2차), sine rms 27.6→26.7px, fast 동일, gesture 손바닥 정지 정상, calib 0.16x 정상 측정.
- 단점: 검출이 0.2초 넘게 끊기면(det 2~5/s) 멈췄다 가는 동작이 됨. 끊김이 잦으면 `--lost-stop 0.35` 처럼 늘려 볼 것.

### 카메라 (확인한 사실)
- `/dev/video0` MJPG 640x480 은 **30fps 지원**, 현재 설정도 30fps (`v4l2-ctl --get-parm`). 컨트롤: `auto_exposure`(3=자동), `exposure_time_absolute`(78~2500, 100µs 단위),
  `exposure_dynamic_framerate`(이미 0), `gain`(0~63), `focus_automatic_continuous`(1 = 자동초점 켜짐).
- 2026-11-20 12:55 확인 때 노출은 다시 자동(3, 29.6~30.5ms)이었음 — 수동 설정이 재연결/재부팅으로 풀린 것으로 보임.
  자동 노출 30ms 는 한 프레임(33ms)과 거의 같아서 블러가 크고 fps 가 떨어질 수 있음.
- 상태줄을 `cam <카메라fps> fps <처리fps> det <검출/s> ... stop <S 횟수> skip <버린 튐 검출>` 으로 바꿈.
  `cam` 이 30 인데 `fps` 가 15 근처면 카메라가 아니라 MediaPipe(CPU)가 한계 → `--proc-width 256` 시도.
- `--exposure 100 --cam-gain 20` 을 주면 시작할 때 v4l2-ctl 로 수동 노출(+dynamic framerate 끔) 설정, **종료할 때 원래 값으로 되돌림**.
  (이때는 기본이 아무것도 안 바꿈이었음 → 오후에 기본값 130/30 으로 변경.) v4l2-ctl 이 없으면 건너뜀 (`sudo apt install v4l-utils`).

**실제 카메라에서는 아직 안 돌려 봄** — 시뮬레이터로만 확인.

### 동작
- 옵션 없이 `aivt run` → 자동 밝기 켜짐. `--exposure` 나 `--cam-gain` 을 주면 그 값으로 고정 (하나만 주면 다른 쪽은 130 / 30, `--exposure 0` = 카메라 자동 노출).
- 시작: 수동 노출 모드로 바꾸고 노출 130 / gain 30 (시험 D 값). 원래 값은 기록해 두었다가 종료할 때 되돌림 (기존 `Camera.release`). 자동 밝기 스레드를 **먼저 멈춘 뒤** 되돌림.
- `AutoBright` 가 별도 스레드에서 0.5초마다 측정·조절 → `v4l2-ctl` 호출이 검출 루프를 막지 않음. 측정 비용은 손 영역 자르기 1번 또는 화면 1/16 축소 1번.
- 노출은 최대한 짧게:
  - 너무 밝으면: 노출을 78까지 먼저 줄이고, 그래도 밝으면 gain 을 0까지 내림.
  - 너무 어두우면: gain 을 먼저 40까지 올리고, 그래도 어두우면 노출을 130까지만 늘림.
- 밝기 기준:
  - 손이 검출되면 손바닥 랜드마크(0,5,9,13,17) 상자 가운데 70% 의 평균. 하얗게 날아간 픽셀(≥250)이 8% 넘으면 너무 밝음.
  - 손이 없으면 화면 전체 평균. 날아간 픽셀이 5% 넘으면 너무 밝음.
- 깜빡임 방지:
  - 목표 120 ±20 안이면 안 바꿈. 한 번에 노출 ×1.12(멀면 ×1.25), gain ±2(멀면 ±4).
  - 날아간 픽셀이 1% 넘으면 어두워도 밝게 하지 않음.
  - 손을 놓친 뒤 2초는 그대로 둠 (손 기준 ↔ 화면 기준이 번갈아 바뀌는 것 방지).
- 상태줄 끝에 `exp 104 gain 30 auto(hand 125)` 표시. 괄호 안은 기준(hand/frame/hold)과 측정 밝기. 고정이면 `exp 130 gain 30 fixed`. 미리보기 글자에도 exp/g 표시.
- 새 옵션: `--bright-target 120`, `--ae-exp-max 130`, `--ae-gain-max 40`.
- 노출을 바꿀 수 없으면(v4l2-ctl 없음, 컨트롤 없음, Mac) 자동 밝기를 끄고 메시지를 출력.
- 캘리브레이션 중에는 자동 밝기를 돌리지 않음 (130 / 30 고정).

### 시뮬레이터 결과 (`python sim.py bright --dur 40`)
가정한 모델: 픽셀 = 반사율 × 장면밝기 × 노출/100 × (1 + gain/32). 바꾼 값은 2프레임 뒤에 반영. 손이 중간중간 사라짐. **실제 카메라의 gain 곡선은 다를 수 있음.**
| 구간 (8s 씩) | 자동: 노출 / gain | 자동: 손 밝기 | 고정 130/30: 손 밝기 |
|:---|:---:|:---:|:---:|
| 보통 | 130 / 30 (변경 0) | 121 | 121 |
| 아주 밝음 ×3 | 130→78 / 30→8 | 140 | **255 (화면 100% 날아감)** |
| 조금 어두움 ×0.8 | gain 8→40 먼저, 그다음 노출 78→123 | 105 | 96 |
| 아주 어두움 ×0.4 | 130 / 40 (상한에서 멈춤) | 56 | 48 |
| 보통 + 창문(화면 31% 날아감) | 손 있을 때 그대로 → 손이 2초 넘게 없으면 노출 130→83 | — | — |
- 노출 범위 78~130, gain 범위 8~40 (상한 지킴). 40초 동안 23번 바뀜. 증가↔감소 방향이 바뀐 3번은 모두 조명이 바뀐 직후. 손 놓친 뒤 2초 안의 변경 0번, 종료 뒤 변경 0번.
- 판단 로직 단독 확인: 밝음 → (104,30)(83,30)(78,30)(78,26)…(78,0). 어두움 → gain 이 40 까지 먼저 오르고 그다음 노출이 98→122→130. 목표 ±20 안이면 안 바꿈.
- 기존 시뮬레이션 회귀 없음: step / sine rms 26.4px / gesture 손바닥 정지 / calib 0.16x 정상.
- 참고: 시뮬레이터는 Python 3.10 이상이 필요함 (`serial_utils.py` 의 `set | None`). Mac 기본 python3 는 3.9 → 이번엔 임시 가상환경(Python 3.11 + numpy, opencv-python-headless, pyserial)으로 돌림.

### 남은 점 / 확인할 것
1. 실제 카메라에서 `aivt run` → 상태줄의 `exp`·`gain`·밝기 값 확인. 밝은 곳(창가)에서 하얗게 날아가지 않는지, 어두운 곳에서 det 가 유지되는지 확인.
2. gain 40 / 노출 130 까지 올려도 어두운 곳은 그 이상 밝아지지 않음 (번짐 방지 때문에 일부러 그렇게 함). 너무 어두우면 `--ae-gain-max 50` 처럼 gain 상한을 먼저 올려 볼 것.
3. 손 영역이 목표 120 에 맞는지(MediaPipe 가 잘 잡는 밝기인지)는 실측 필요 → `--bright-target`.
4. 창문처럼 밝은 배경: 손이 2초 넘게 없으면 화면 기준으로 노출을 줄임 → 손이 다시 나오면 어두워졌다가 다시 밝게 맞춤 (몇 초).
5. 조명이 크게 바뀌면 맞추는 데 수 초 걸림 (0.5초마다 조금씩이라서). 너무 느리면 한 번에 바꾸는 양을 늘리는 것 검토.
6. 위 "가끔 끊김" 후보 2가지(검출 사이 예측으로 잇기, 감속 정지)는 아직 그대로.
